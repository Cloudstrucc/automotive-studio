Chapter 1

What Autoline is

A storefront for a pre-owned vehicle dealer in Ottawa, and an admin app the dealer uses to run it. The storefront is a static site with no server and no database. The admin is a single Cloudflare Worker. Between them sits one GitHub repository, which is the only database either of them has.

Two things are worth establishing before anything else, because every other decision in this book follows from them.

The repository is the database

There is no Postgres, no Firebase, no CMS. A vehicle is a JSON file. Its photos are JPEGs next to it. A category is a JSON file. When the dealer publishes something in the admin, the Worker writes those files into the repository as a git commit. When they delete something, it deletes files. The site is then rebuilt from whatever files exist.

This means every change is a commit, with an author, a timestamp and a diff; anything can be reverted with git revert; and the whole state of the business can be read by anyone who can read JSON.

Rendered ads are generated, not uploaded

The dealer never makes an image. They type a year, a price, some specs, and upload a photo of the car. A Python generator composes that into three finished advertisement images — one portrait for phones, one square-ish for social, one widescreen — with the price, the specs and the contact details drawn onto them in the Velocity house style. Those generated images are what the public site shows and what the dealer downloads to post elsewhere.

The one-line version

Dealer types a car into a web form → Worker commits JSON + photo to GitHub → GitHub Actions renders three ad images and rebuilds the site → GitHub Pages serves it. About a minute, end to end, with no human in the middle.

Chapter 2

Architecture

Two halves that never talk to each other directly. They communicate only by one of them committing files that the other later reads.

The four moving parts

PartTechnologyJobWhere it runs
build.pyPython 3, standard library only Turns manifests + rendered ads into a static siteGitHub Actions, and a developer machine
tools/Python + Playwright + Chromium Draws the ad SVGs and renders them to JPGGitHub Actions, and a developer machine
admin/worker/JavaScript on Cloudflare Workers Serves the admin UI, calls Anthropic, commits to GitHubCloudflare's edge
deploy.ymlGitHub Actions Orchestrates render → build → deploy on every pushGitHub
Why build.py uses no dependencies

It is standard library only, deliberately. CI installs nothing to build the site, so the build cannot break because a package moved. Playwright is needed only to render ads, which happens only when a manifest or photo changed — most pushes skip it entirely.

What Wrangler is

Worth stating plainly, because the name suggests more than it is.

Wrangler is Cloudflare's command-line tool for Workers. It is not a web framework, it is not what the site is built with, and it has nothing to do with GitHub Pages. It does exactly two things in this project:

  • npx wrangler deploy — uploads admin/worker/ to Cloudflare.
  • npx wrangler secret put NAME — stores a secret the Worker can read.

admin/worker/wrangler.toml is its configuration file: the Worker's name, which file is its entry point, the non-secret variables, and a rule that lets worker.js import workspace.html as a string so it can be served from GET /.

The two halves use completely separate tooling

The public site is Python + GitHub Actions + GitHub Pages. No Node, no Wrangler, no Cloudflare. The admin is JavaScript + Wrangler + Cloudflare Workers. No Python. The only thing they share is the repository.

Chapter 4

The data model

Four kinds of file, three of which a human ever writes. Everything the site shows is derived from them.

An item — one product

Path: <env>/manifests/items/<category>/<slug>.json. The folder it sits in is its category, and the file name is its slug, which becomes its URL.

{
  "schema": 1,
  "slug": "santafe",
  "catalogue": "vehicles",
  "status": "published",
  "order": 1,
  "make": "Hyundai",
  "model": "Santa Fe Sport",
  "year": "2017",
  "subtitle": "2.4L · Heated Seats",
  "price": "14,000",
  "eyebrow": "Pre-Owned",
  "kicker": null,
  "specs": [
    { "label": "KM",         "value": "107,000" },
    { "label": "Engine",     "value": "2.4L" },
    { "label": "Drivetrain", "value": "FWD" }
  ],
  "images": [
    { "file": "source-photos/vehicles/santafe/1.jpg", "role": "primary" }
  ],
  "background": "source-photos/vehicles/santafe/blur.jpg",
  "audit": { "updated_at": "2026-10-18T14:02:11.004Z" }
}

images[].file is relative to the environment root, not to the manifest. Exactly three specs are drawn on the ad — the three columns across its middle — and the labels come from the item's category.

A category

Path: <env>/manifests/catalogues/<slug>.json. Note the folder is spelled catalogues — the word the code uses internally — while the admin says category to the dealer. They are the same thing.

{
  "schema": 1,
  "slug": "vehicles",
  "status": "public",
  "label": "Vehicles",
  "mark": "VE",
  "order": 1,
  "in_menu": true,
  "heading": "The Lineup",
  "lede": "Pre-owned vehicles for Ottawa drivers, priced to move.",
  "spec_slots": [
    { "label": "KM" }, { "label": "Engine" }, { "label": "Drivetrain" }
  ]
}

Source photos

Path: <env>/source-photos/<category>/<slug>/1.jpg, numbered upward. The admin resizes every upload to 1600px on its long edge in the browser before it is ever sent, because the generator never composites above 1920px and a 12-megapixel phone original is wasted bytes in a commit.

blur.jpg, if present, is a small heavily downscaled copy used as the frame-filling backdrop behind the car. Without one the first photo stands in — it is blurred and veiled anyway, so the difference is file size, not appearance.

Generated ads

Paths: <env>/ads/svg/<slug>_<format>.svg and <env>/ads/jpg/<slug>_<format>.jpg. Three formats per item:

FormatPixelsRatioShown to
phone1080 × 23409:19.5Viewports under 560px
social1080 × 13504:5560px and up
landscape1920 × 108016:9900px and up

The item page picks one with a <picture> element, so a phone downloads only the phone ad. All three, plus their SVGs, are also bundled into <slug>-ads.zip for the dealer to download and post elsewhere.

The images are the source of truth for their own text

Year and price shown in the surrounding HTML are parsed back out of the SVG by ad_facts() in build.py. The price is never written into the page from the manifest separately. One number, one place, no chance of the page and the picture disagreeing.

cars.json — legacy

Each environment still has one. It predates manifests and could override a display name, subtitle, order, year or price. Nothing writes it any more and it can be ignored; it is kept because removing it is a change with no benefit.

Chapter 5

Categories & routes

A category is a group of things the dealer sells. It gets its own page, its own URL and its own three spec labels. One category is special.

Vehicles is the default, and has no route of its own

vehicles is the environment. Its board is the environment's index page and its items sit under cars/. There is deliberately no /vehicles/ URL. Every other category lives in a folder named after its slug, with its board and its item pages together.

CategoryBoardItem pageZip
vehicles default <env>/index.html <env>/cars/<slug>.html <env>/cars/<slug>-ads.zip
any other, e.g. tyres <env>/tyres/index.html <env>/tyres/<slug>.html <env>/tyres/<slug>-ads.zip

Both item folders sit exactly one level under the environment root, which is why ad images are ../ads/jpg/… from every item page and no stylesheet path had to change when categories were introduced.

Why vehicles has no route

So that none of today's URLs moved. A link to /automotive-studio/cars/sienna.html that someone sent a buyer in October still works. Adding a category must never break the links already in the world.

Reserved names

A category cannot take a folder the build already writes at an environment root: ads, assets, cars, or any environment name (production, review, development). The admin refuses to create one; build.py skips it with a warning if it finds one anyway.

The menu

A category is listed in the site's top menu only when all three are true: its status is public, its in_menu flag is on, and it has at least one published item with a photo.

And the menu is only drawn at all once two categories qualify. One entry is not a menu — it is the page already on screen. This is why the site today, with only Vehicles, carries no menu markup whatsoever and looks exactly as it did before categories existed.

in_menu is the sitemap flag

Turning it off leaves a category fully published and reachable by direct link, but out of the menu. Useful for a seasonal or wholesale list meant for specific people without putting it in front of every visitor.

Chapter 6

States & lifecycle

Categories have three states. Items have two. The asymmetry is deliberate and this chapter explains it, because it is the thing most likely to look like an oversight.

Category status

StatusRendersIn the menuMeans
publicYes, at its own routeIf in_menu and it has an item Live
draftNoNoNot launched yet
retiredNoNoWe stopped selling this

published is the pre-migration spelling of public and is still read as public, so a manifest written before the three states existed keeps building.

draft and retired behave identically in the build — both render nothing. They are kept apart purely because they read differently to the owner in the admin list. Nothing in the build branches on which one it is.

Item status — two states, not three

An item is published or draft. That is the whole vocabulary. The single off-the-site state is reached two ways:

  • Save as a draft at creation — written, never on the site.
  • Deactivate an item that was live — same state, reached later.

The original specification asked for draft, publish and disable as three distinct ideas. For a category three states earn their keep, because the owner reads that list as a plan. For an item they do not: draft and a hypothetical retired would be the same row in build.py, the same row in gen_velocity.py, the same affordances in the admin, and the same thing to the dealer — saved here, not on the site. A third spelling would mean two words for one behaviour and two code paths that must never diverge.

Recording why something is off the site

Sold, awaiting photos, seasonal — that is a different fact from whether it renders, and it belongs in a field of its own, not in the gate that decides rendering.

The rule both renderers agree on

An item renders only when

its status is published, and it has at least one image, and its category's status is public.

build.py and tools/gen_velocity.py both enforce this independently. A change to it must be made in both, or the site and the ads will disagree about what exists.

The orphan pen

Deleting a category must not destroy what it held. In the one commit that removes the category manifest, each of its items is rewritten to manifests/items/orphan/<slug>.json with catalogue: "orphan", status: "draft", and audit.orphaned_from recording where it came from.

orphan is not a real category. It has no manifest, no route and no menu entry. build.py skips it whatever the items' own status says, gen_velocity.py renders no ads for it, and the Worker refuses to commit a published item into it. The admin shows orphaned items in a tile of their own so they can be given a category again — which is an ordinary edit plus an explicit publish.

Chapter 7

The publish pipeline

What happens between the dealer pressing Publish and a buyer seeing the car. Roughly sixty seconds, with five distinct actors.

Why only some pushes re-render

The workflow diffs the previous push against this one and re-renders only environments whose manifests/ or source-photos/ changed. Editing build.py or this document renders nothing; it just rebuilds and deploys, in about twenty seconds.

And why only some ads re-render

This is worth understanding because it was a real problem for a while. SVG generation is deterministic: the same manifest always produces the same bytes. JPEG rendering is not — headless Chromium loads the Google webfonts a little differently each run, so re-rendering an untouched ad yields a JPG that differs by a fraction of a percent.

Left alone, that meant every manifest edit rewrote all fifteen JPGs in that environment, producing noisy commits and binary merge conflicts whenever a local regeneration raced a CI one.

So the SVGs are used as the signal instead. sync_ads.py compares each freshly generated SVG against the one committed at <env>/ads/svg/. An ad whose SVG matches is left completely alone — not rendered, not copied, byte-for-byte the file already in git. Only genuinely changed ads are re-rendered.

The guarantee

Running ./tools/regen.sh again without changing anything produces an empty diff. Change one vehicle's price and exactly that vehicle's three SVGs and three JPGs change.

The cost

A revert does not restore a JPG's original bytes: going back changes the SVG back, which means a fresh render. Use git checkout <env>/ads to undo an unwanted regeneration, rather than regenerating back to the previous state.

Chapter 8

Environment map

Three environments, one branch, one Worker. That last part surprises people, so it is worth stating up front.

There is only one branch, and only one Worker

Environments here are folders, not branches and not deployments. Everything lives on main. One push rebuilds all three sites. One Worker serves the admin, and it writes to development only. Branch-per-environment intuitions do not apply here.

EnvironmentFolderBranchPublic URLPurpose
Production production/ main …/automotive-studio/ and …/production/ Approved. What a buyer sees.
Review review/ main …/automotive-studio/review/ Client sign-off. Shared by direct link.
Development development/ main …/automotive-studio/development/ Work in progress. Where the admin writes.

The root mirrors production

PUBLIC_ENV in build.py is "production", and the site root is a complete copy of it. A client opening the bare URL never sees an environment name in the text or in any path.

The site never names an environment

No badges, no labels, no "Production" in a title or a breadcrumb. Every board is just "The Lineup". The folder names survive only in URLs and in ENVS in build.py. New pages must keep it that way — this is a client-facing product, and the plumbing is not the client's business.

Chapter 9

Promotion

Moving approved work from development to review, and from review to production. Done from the admin app. No commands, no checkout, nothing to copy by hand.

What promotion copies

CopiedNot copied
The item manifestRendered ads (<env>/ads/)
Every source photo it referencesItems in the orphan pen
Its backdrop, if it has oneAnything outside the two environments named
Its category manifest, if the target lacks it
Ads are re-rendered, never inherited

The target environment's artwork is always built from the manifests the target itself holds. CI re-renders any environment whose manifests/ or source-photos/ changed, so a promotion triggers exactly the render it needs. This is what keeps an environment internally consistent instead of carrying images produced somewhere else.

Doing it

  1. Workspace → Promote

    The tile sits next to the categories.

  2. Choose the target

    Review for client sign-off, Production for the live site. Choosing production shows a warning saying so, because it is the one action in the admin that changes what buyers see.

  3. Choose what to send

    Everything is selected by default, grouped by category. Clear the checkbox on anything that should stay behind. The button counts what is selected.

  4. Promote

    One commit. The confirmation reports how many items and files moved, and a chip tracks the re-render until it reports Live on the site.

Drafts promote as drafts

A draft item is copied across still marked draft, so it does not appear on the target until it is published there. This makes it safe to promote a whole environment without auditing each item's state first — nothing becomes visible that was not already visible.

Why no bytes move

Promotion runs in the Worker, not the browser, and it does not upload anything. Every file it copies is already in the repository, so it builds a git tree whose entries point at the same blob SHAs. Promoting a vehicle with four photos transfers no image data at all — it is a few API calls regardless of how large the photos are.

This is also why promotion is not bound by ALLOW_PREFIXES

POST /api/promote never accepts a path from its caller. It takes an environment name, which must be one of three known values, and a list of slugs, which must match ^[a-z0-9][a-z0-9-]*$. Every path it writes it constructs itself. That is a tighter constraint than a prefix list, which is why adding promotion allowed the general write allowlist to be narrowed rather than widened — see chapter 20.

What promotion refuses

RefusedStatusReason
A published item with no photo422 It would render as an empty frame on the target
An item whose photo is missing from the repository422 The target would reference a file that is not there
Same source and target400Nothing to do
An unknown environment name400Only the three are accepted
A slug containing anything but a-z0-9-400 Closes path traversal at the door
More than 200 files in one commit413Promote fewer items at a time

Every refusal happens before any commit, so a rejected promotion changes nothing. These guardrails are covered by tests — admin/worker/promote.test.mjs, run with bash admin/worker/test-promote.sh.

Promoting by hand

Still possible, and occasionally useful — restoring one environment from another, or moving something the admin will not touch. The shape is: copy the manifest and the photos, regenerate the target, commit.

SLUG=sienna
cp development/manifests/items/vehicles/$SLUG.json review/manifests/items/vehicles/
mkdir -p review/source-photos/vehicles/$SLUG
cp development/source-photos/vehicles/$SLUG/* review/source-photos/vehicles/$SLUG/

./tools/regen.sh review          # renders only what changed
python3 build.py                 # check it locally before pushing
git add -A && git commit -m "Promote $SLUG to review" && git push

Pushing the manifests alone would also work — CI regenerates the target either way. Running regen.sh first simply means the diff under review is the finished one.

Comparing two environments

After a full promotion all three environments generate byte-identical SVGs. Their JPGs will still differ slightly — that is the render non-determinism from chapter 7, not a content difference. Compare SVGs, not JPGs, to find out whether two environments really match.

Promotion is a decision, not a schedule

It is deliberately a button someone presses, not an automatic flow from development to production. The entire value of three environments is that something stands between the dealer's keyboard and the live site. Automating the whole chain would leave one environment with extra steps.

Chapter 10

Administering GitHub

Pages, Actions, permissions and the token. Set once; revisit when the token expires.

Pages

  1. Settings → Pages → Build and deployment

    Source must be GitHub Actions, not "Deploy from a branch". If it is set to a branch, the workflow will run green and nothing will ever change on the site, which is a confusing failure.

  2. Confirm the URL

    https://cloudstrucc.github.io/automotive-studio/. For a user or organisation site the path differs; for this project repository the repo name is in the path, and build.py writes relative links throughout so it does not need to know.

  3. Check .nojekyll exists at the repo root

    Without it, Pages runs Jekyll over the output and silently drops anything in a folder starting with an underscore.

Actions permissions

The workflow commits re-rendered ads back to the repository, so it needs write access:

permissions:
  contents: write      # the ad regeneration commits its output back
  pages: write
  id-token: write

And in Settings → Actions → General → Workflow permissions, "Read and write permissions" must be allowed. If this is set to read-only, the render step fails at the push with a 403.

The GitHub token for the Worker

Create at github.com/settings/personal-access-tokens/new — a fine-grained token, not a classic one.

SettingValue
Resource ownerCloudstrucc
Repository accessOnly select repositories → automotive-studio
Permissions → ContentsRead and write
Everything elseNo access
Expiration90 days — the renewal belongs in a calendar

Then store it on the Worker:

cd admin/worker
npx wrangler secret put GITHUB_TOKEN
When the token expires the admin stops publishing

The failure looks like a 401 or 403 from /write in the admin, with the site otherwise fine. Rotate the token and run wrangler secret put GITHUB_TOKEN again. Nothing else needs changing.

Reading what CI did

# recent runs
gh run list --limit 5

# watch the current one
gh run watch --exit-status

# why did that one fail?
gh run view --log-failed

Chapter 11

Administering Cloudflare

One Worker, deployed with Wrangler, with three secrets and an Access policy in front of it.

Prerequisites

  • A Cloudflare account (free plan is enough).
  • Node.js on the developer machine — only to run npx wrangler. Nothing in the project is a Node application.
  • Signed in: npx wrangler login opens a browser once and stores the credential.

Deploy

cd admin/worker
npx wrangler deploy

It prints the bindings it found and the URL it deployed to:

Uploaded autoline-write (1.95 sec)
Deployed autoline-write triggers (0.74 sec)
  https://autoline-write.cloustrucc.workers.dev
Current Version ID: 42cb0a6f-6b2c-4b74-9d41-79bd0aac5050
Deploying is separate from pushing

Committing a change to worker.js or workspace.html does not deploy it. There is no CI for the Worker; npx wrangler deploy is a manual step, and an easy one to forget after changing the admin UI. An admin that appears to ignore a committed change has almost always not been redeployed.

Secrets

npx wrangler secret put GITHUB_TOKEN        # fine-grained PAT, one repo, Contents: RW
npx wrangler secret put ANTHROPIC_API_KEY   # for POST /api/plan

# optional, only if scripts need to call /write from outside Access:
openssl rand -base64 32 | tr -d '\n' | pbcopy && echo "copied to clipboard"
npx wrangler secret put WRITE_KEY

# see which secrets exist (names only — values are never shown again)
npx wrangler secret list
Secrets are write-only

Cloudflare never shows a secret again once it is set. Losing one means setting a new one, not recovering the old. Where there is any doubt that WRITE_KEY is a long random value, replace it — a short guessable key on an endpoint that can commit to the repository is the worst failure mode in this system.

If a deploy goes wrong

Chapter 12

Access & who can sign in

Cloudflare Access authenticates a visitor before the request ever reaches the Worker. This is the admin's front door, and it currently has one working key.

How the gate works

There is no login code in the Worker. Access sits in front of the whole hostname and authenticates first; requests that get through carry a Cf-Access-Jwt-Assertion header, which the Worker reads to know who is signed in.

Writes additionally fail closed on their own: POST /api/plan and POST /write return 401 unless the request carries that assertion or a valid WRITE_KEY. So a Worker with Access misconfigured leaks the UI, not the ability to publish.

Same-origin is deliberately not accepted as authentication

An earlier version trusted same-origin requests. Since the page itself is public, every visitor is same-origin — that was an open write endpoint for anyone who found the URL. It was fixed within minutes, and the lesson is worth keeping: being served by the same host proves nothing about who is asking.

Setting the policy up

  1. Zero Trust → Access → Applications → Add an application → Self-hosted
  2. Domain

    autoline-write.cloustrucc.workers.dev

  3. Policy: Allow

    Action Allow, with an Include rule of Emails listing the administrator and the dealer.

  4. Identity provider

    This is the part that is not finished — see below.

The One-time PIN gap

Today the dealer cannot sign in

The only identity provider currently enabled requires a Cloudflare account. The dealer does not have one, and sees "Cloudflare sign-in is restricted to members of the account." Listing their email in the policy is not enough on its own — they need a way to authenticate, and One-time PIN is that way.

To fix it: Zero Trust → Settings → Authentication → Login methods → Add new → One-time PIN. It needs no configuration; the user receives a code by email.

Then confirm the application's policy has the dealer's email in an Include rule. Adding One-time PIN under Require forces that method specifically.

Do not put One-time PIN in Include without an email restriction

An Include rule of "One-time PIN" alone means anyone with any email address can get a code and sign in. Keep the email list in Include and the method in Require.

Branding the login page

Customisation is account-wide, not per application — the Cloudflare docs are explicit that changing it updates the login page for every Access application on the account. Path: Zero Trust → Reusable components → Custom pages → Access login page. It covers the organisation name, a logo, header and footer text, and a background colour.

Two genuinely per-application controls do exist: App Launcher customisation, and custom block pages. On an account with only this one application, the account-wide limitation costs nothing.

Signing out

The admin's profile screen links to /cdn-cgi/access/logout, which is Access's own endpoint. The Worker has no session of its own to end.

Chapter 15

Edit, deactivate, delete

Everything that can be done to a product that already exists, and which of those actions are reversible.

The category list

Opening a category gives a row per item. Each row shows its name, subtitle and price, with tags for no photo and deactivated. Pressing the row opens the item for editing in place. Each row carries three actions:

Share

Copies that item's public URL to the clipboard, ready to paste into a message. It does not open a tab.

Deactivate / Activate

Takes the item off the site, keeping everything. Fully reversible.

Delete

Removes the manifest and source photos for good. Asks once; cannot be undone from the admin.

Editing

Editing an item redraws its ads

There is nothing to regenerate by hand. Publishing an edit writes the manifest; CI re-renders that item's three ads from the new values and rebuilds the site, and the deploy chip reports when it has landed. The same is true after a promotion, in the environment it landed in.

Press the row. The item opens with its fields filled in. Existing photos are kept unless new ones are added — adding any photo replaces the whole set, it does not append. The slug, the order and the kicker are preserved, so editing never moves an item or breaks its URL.

An edit keeps the item's current status

Saving a deactivated item does not quietly put it back on the site. If it was a draft before the edit, it is a draft after. Use Activate to change that deliberately.

Deactivating

Writes status: "draft" and changes nothing else. On the next build the item disappears from the site. Activating it later brings it back exactly as it was — same photos, same fields, same URL.

The rendered ads are deliberately left in place. CI rebuilds <env>/ads/ from whatever manifests remain, so they vanish from the site on the next build without the admin needing write access to the ads folder at all.

Activating needs a photo

The Activate button is disabled for an item with no photo, and the Worker refuses the write as well. Add a photo first by editing the item.

Deleting

Removes the item's manifest, its source photos and its backdrop in one commit. The rendered ads are cleaned up by the next regeneration, because sync_ads.py deletes ads whose item is gone.

Delete is permanent from the admin's point of view

There is no undo button. It is recoverable from git — git revert the commit — but that is a developer action, not something the dealer can do. Prefer Deactivate unless the removal is certain.

Chapter 16

Manage categories

Adding a new line of business, and retiring one that has ended, without a deploy.

Creating one

  1. Workspace → New category
  2. Name it

    The slug is derived as the name is typed — "Winter Storage" becomes winter-storage, which is the folder and the URL. It is shown under the field so there are no surprises.

  3. Heading and blurb

    Both are printed on that category's page. The heading is the big title; the blurb is the line under it.

  4. Three spec slots

    The three labels every item in this category will use — the three columns drawn across the middle of every ad. Vehicles uses KM · Engine · Drivetrain. Three is required, not a suggestion.

  5. State and menu

    Choose On the site, Draft or Retired, and whether it appears in the site's menu. Chapter 6 covers what each means.

  6. Create

    One commit writes development/manifests/catalogues/<slug>.json and the admin opens the new, empty category.

A new category shows nothing until it has an item

The menu entry needs at least one published item with a photo, and the menu itself only appears once two categories qualify. An empty category is a tile in the admin and nothing on the site, which is the right default.

Deleting one

Deleting a category never destroys what it held. In a single commit, the category manifest is removed and each of its items is rewritten into the orphan pen as a draft, with audit.orphaned_from recording where it came from.

Orphaned items appear in the admin under their own tile. Give one a new category from its category dropdown, publish it, and it is back. Deleting an empty category just removes its manifest.

The category dropdown on items

Every item has one. Created from inside a category, it is pre-set and needs no attention. Created from anywhere else, it is empty and must be chosen before the item can be published. It is also how an orphaned item is reassigned.

The Worker checks the dropdown agrees with the folder

/write refuses a published item whose catalogue is missing, is orphan, or disagrees with the folder its manifest is being written into. A manifest and its location can never drift apart.

Chapter 18

Worker API

Five routes. The page is served by the same Worker that serves the API, which is the whole reason this architecture works at all.

GET/

The workspace page. workspace.html is imported as a string via the [[rules]] type = "Text" rule in wrangler.toml and returned as HTML. There is no login here — Access gates it, and the page itself is harmless.

GET/api/me

Decodes the Cf-Access-Jwt-Assertion header and returns who is signed in.

{ "ok": true, "email": "fred@example.com", "expires": "2026-11-23T09:00:00Z" }

GET/api/items?env=development

One recursive git-tree call finds every manifest, then their blobs are fetched in parallel. Nothing is cached, so the admin always shows what is actually committed.

{
  "ok": true,
  "env": "development",
  "count": 5,
  "catalogues":    { "vehicles": [ { …item…, "_path": "…", "_catalogue": "vehicles" } ] },
  "catalogueDefs": [ { …category manifest…, "_path": "…" } ]
}

Fields prefixed with _ are added by the Worker and are not part of the stored manifest. Strip them before writing a manifest back.

POST/api/plan

Takes a plain-English description and returns validated plan JSON. Calls Anthropic server-side with claude-sonnet-5-5; the API key never reaches the browser. Returns 503 if ANTHROPIC_API_KEY is not set — the rest of the admin keeps working, with the fields typed in by hand.

{
  "summary": "one sentence describing the change",
  "fields": {
    "title": "…", "subtitle": "…", "year": "…",
    "price": "digits and commas only, no $",
    "eyebrow": "a short badge like Certified",
    "specs": [ { "label": "…", "value": "… or null" } ]
  }
}

POST/write

Files and deletions in, one commit out, via the GitHub git data API: blobs → tree → commit → ref update. Either the whole set lands or none of it does, so the repository is never half-updated and the site rebuilds once.

{
  "message": "Add 2018 Honda Civic in development",
  "files": [
    { "path": "development/manifests/items/vehicles/civic.json",
      "contentsBase64": "eyJzY2hlbWEiOjEs…" },
    { "path": "development/source-photos/vehicles/civic/1.jpg",
      "contentsBase64": "/9j/4AAQSkZJRgABA…" }
  ],
  "deletes": [ "development/manifests/items/vehicles/old.json" ]
}

Responses

StatusMeaningWhat to do
200{ ok: true, commit: "…" }Done
401No Access assertion and no valid WRITE_KEY Sign in, or check Access is configured
403A path is outside ALLOW_PREFIXES The allowlist is doing its job; do not widen it casually

POST/api/promote

Copies items from one environment to another. Takes no paths — it builds every path itself from a validated environment name and a slug, which is why it is not bound by ALLOW_PREFIXES (chapters 9 and 20).

{
  "from":  "development",
  "to":    "review",
  "slugs": ["santafe", "elantra"]      // omit to promote everything
}

Responds { ok, commit, promoted, files, from, to }. It uploads nothing: the new tree points at blobs already in the repository. Refusals are listed in chapter 9 and all happen before any commit.

GET/api/build

The most recent workflow run on the branch, so the admin can say whether a change has finished rendering rather than leaving someone reloading the public site.

{
  "ok": true,
  "state": "in_progress",        // queued | in_progress | success | failure | cancelled | none
  "title": "Add 2018 Honda Civic in development",
  "url": "https://github.com/…/actions/runs/123",
  "started": "2026-11-22T10:04:11Z",
  "sha": "408aa03…"
}

The admin polls this every 8 seconds after a write, for up to about four minutes, and stops as soon as the run settles.

Auth, precisely

const viaAccess = !!request.headers.get('cf-access-jwt-assertion');
const viaKey    = env.WRITE_KEY && timingSafeEqual(auth, `Bearer ${env.WRITE_KEY}`);
if (!viaAccess && !viaKey) return json({ error: 'unauthorized' }, 401);

Fail-closed, and same-origin is not in that expression on purpose.

Chapter 20

Security model

What stops a leaked credential from becoming a compromised website.

The path allowlist is the real boundary

ALLOW_PREFIXES = "development/manifests/,development/source-photos/"

Nothing outside those prefixes can be written by POST /write. Even with the Worker's GitHub token in hand, an attacker cannot reach .github/workflows/, build.py, tools/ or assets/. A leaked credential cannot make the site build unreviewed code — only add or change content in one environment, which a glance at the diff reveals.

It used to be manifests/,source-photos/,development/, which also permitted writes to development/ads/ — the generated artwork. The admin never writes an ad, so allowing it bought nothing and widened the blast radius.

Promotion made this narrower, not wider

The obvious way to let the admin reach review and production would have been to add them to this list. Instead POST /api/promote takes no caller-supplied paths at all: an environment name from a set of three, and slugs matching ^[a-z0-9][a-z0-9-]*$. Every path is constructed server-side. A narrow validated operation beats a wider prefix list.

Do not widen this to add a feature

If something needs to write outside these prefixes, that is a signal the feature belongs somewhere else — in CI, or in a developer's hands. The allowlist is the one thing standing between a content tool and arbitrary code execution on a public site.

Defence in depth

LayerStops
Cloudflare AccessStrangers opening the admin at all
Fail-closed auth on writesA misconfigured Access from becoming an open write endpoint
ALLOW_PREFIXESAny write reaching code or workflow files
Path traversal rejection../ escaping the allowlist
Image guardrailA published item with nothing to show
Category guardrailA manifest drifting from its folder, or publishing into the orphan pen
Fine-grained tokenThe blast radius reaching any other repository
Atomic commitsA half-written state the site could build from

Secret handling

  • Secrets live only in Cloudflare, set with wrangler secret put, never in the repository and never shown again.
  • .dev.vars is gitignored and must stay that way.
  • The Anthropic key is used server-side only; the browser never sees it.
  • WRITE_KEY is optional. If set, make it 32+ random bytes — it is a bearer token that can commit to the repository.
Two incidents worth remembering

The open endpoint. The first Worker trusted same-origin requests. The page is public, so every visitor qualified — an open write endpoint for roughly four minutes until it was spotted and fixed. Hence the rule in chapter 12.

The HAR file. A browser export pasted into a chat to debug a 401 contained live session cookies for an unrelated service. A HAR should be scrubbed before sharing, or the single failing request shared instead. Treat any HAR as a credential dump until proven otherwise.

Routine hygiene

  • Rotate GITHUB_TOKEN every 90 days; diarise it.
  • Review the Access policy's email list when someone leaves.
  • Skim git log --author="autoline" occasionally — every admin write is a commit, so the audit trail is already there.

Chapter 22

Design decisions

Why this is shaped the way it is. The plan documents in docs/ are the long form; this is what survived contact with reality.

Why not a real admin application?

docs/ADMIN_PLATFORM_PLAN.md and docs/ADMIN_APP_PLAN.md planned a conventional app: Node, SQLite, sessions, magic links, a job queue. Both were abandoned for the same reason — the public site is static and free, and every one of those pieces adds something to run, pay for, patch and back up, to manage five vehicles.

Git already provides the durable store, the audit log, the rollback and the access control. Building a database next to it would have meant keeping two sources of truth in sync.

Why not a published Artifact?

docs/OPTION_B_PLAN.md is a complete design for the admin as a Claude Artifact. It cannot work, and the reason is worth recording because it is not obvious:

Content-Security-Policy: connect-src 'self' https://<id>.frame.claudeusercontent.com

An Artifact may talk to itself and nothing else, whatever CORS headers an external endpoint returns. No amount of server-side configuration changes that. Serving the page from the same origin as the API removes CSP and CORS from the picture entirely — which is exactly what the Worker does, and why the page lives inside wrangler.toml's text rule rather than anywhere else.

Why a Cloudflare Worker?

  • It can serve the page and the API from one origin — the thing the Artifact could not do.
  • Secrets stay server-side; the browser never holds the GitHub token or the API key.
  • Access gives real authentication with no login code to write or get wrong.
  • Free at this scale, and nothing to patch.

Why categories became repository data

They started as a hardcoded array in workspace.html. That meant the dealer could not add one without a developer and a deploy, which made "add a category" a support ticket. Moving them to manifests made it a commit like everything else — and gave them states, a sitemap flag and a safe delete in the process.

Why the ads are generated rather than uploaded

Consistency, and because the dealer is not a designer. Every ad is drawn by the same code, so the brand holds without anyone policing it. It also means a global change — a new phone number, a layout fix — is one edit and one command, not fifteen trips through Photoshop.

What the docs/ folder is for now

FileStatus

docs/ADMIN_PLATFORM_PLAN.mdHistorical — the conventional-app plan
docs/ADMIN_APP_PLAN.mdHistorical — its v2
